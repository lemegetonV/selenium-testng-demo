## The design

A custom Log4j2 appender forwards log events from `com.demowebshop.*` 
loggers into the currently-active ExtentTest node. The listener 
publishes the current ExtentTest to a shared ThreadLocal on 
onTestStart; the appender reads it on every log event.

### Classes to create

**1. `com.demowebshop.listeners.CurrentExtentTest`** — small static 
holder for `ThreadLocal<ExtentTest>`.

    public final class CurrentExtentTest {
        private static final ThreadLocal<ExtentTest> CURRENT = new ThreadLocal<>();
        
        private CurrentExtentTest() {}
        
        public static void set(ExtentTest test) { CURRENT.set(test); }
        public static ExtentTest get() { return CURRENT.get(); }
        public static void clear() { CURRENT.remove(); }
    }

Minimal class; no logic beyond holder. Javadoc explaining its purpose 
(bridge between ExtentReportListener and ExtentAppender without 
creating a hard coupling between the two).

**2. `com.demowebshop.listeners.ExtentAppender`** — custom Log4j2 
plugin appender. Extends `AbstractAppender`. Key behaviors:

  - Registered as a Log4j2 plugin with `@Plugin(name = "ExtentAppender", 
    category = Core.CATEGORY_NAME, elementType = Appender.ELEMENT_TYPE)`
  - Static factory method `createAppender(String name, Filter filter, 
    Layout<? extends Serializable> layout)` annotated with 
    `@PluginFactory`
  - In `append(LogEvent event)`:
    1. Read `CurrentExtentTest.get()`. If null, return silently — logs 
       emitted outside a test (e.g. during @BeforeSuite) are not report 
       material.
    2. Map Log4j level to Extent log level:
       - INFO → extentTest.info(message)
       - WARN → extentTest.warning(message)
       - ERROR → extentTest.fail(message)
       - DEBUG/TRACE → skip (keeps the report focused on user-visible 
         narrative; file/console logs still capture them)
    3. Extract the formatted message via `event.getMessage()
       .getFormattedMessage()` (handles SLF4J placeholder substitution)
    4. Call the appropriate Extent method with the message string.
  - No layout dependency at runtime (we're passing strings to Extent, 
    not formatting for console). Accept the layout parameter in the 
    factory for plugin-contract compliance but don't use it.
  - No try/catch around the Extent call — if Extent throws, the 
    framework should fail loudly, not swallow. Wrap only the 
    `CurrentExtentTest.get()` null-check path to be defensive.

Keep this class under 80 lines. It does one thing.

### Integration changes

**3. Update `log4j2.xml` in `src/main/resources/`:**

  - Add the custom appender registration. The `packages` attribute on 
    the root `<Configuration>` element must include 
    `com.demowebshop.listeners` so Log4j2 plugin discovery finds the 
    appender class:
    
        <Configuration status="WARN" packages="com.demowebshop.listeners">
    
  - Add the appender element. Name it "ExtentAppender". No layout 
    needed.
  - Attach it ONLY to the `com.demowebshop` logger — not root, not 
    Selenium loggers. This prevents noise like Chrome DevTools 
    messages from bleeding into the report.
  - Keep Console and RollingFile appenders and their existing attachments
    untouched.

  The relevant logger block becomes something like:
  
      <Logger name="com.demowebshop" level="DEBUG" additivity="false">
          <AppenderRef ref="Console"/>
          <AppenderRef ref="RollingFile"/>
          <AppenderRef ref="ExtentAppender"/>
      </Logger>

  Note: additivity="false" prevents double-logging if the root logger 
  also has Console attached.

**4. Update `ExtentReportListener`:**

  - In `onTestStart(ITestResult)`: after creating the ExtentTest node 
    and pushing it to the listener's own ThreadLocal, also call 
    `CurrentExtentTest.set(extentTest)`.
  - In `onTestSuccess`, `onTestFailure`, `onTestSkipped`, AND 
    `onTestFinish` (whichever covers end-of-test per current listener 
    structure): call `CurrentExtentTest.clear()` at the very end, 
    after the existing pass/fail/skip logic.
  - Do NOT remove the listener's existing internal ThreadLocal — that 
    still handles screenshot attachment on failure. 
    `CurrentExtentTest` is a parallel mechanism for the appender to 
    read from; decoupling is intentional.

## What NOT to do

- No screenshots on every step. Screenshots remain on failure only. 
  That's still the right default.
- No "step grouping" via ExtentTest.createNode() for the test section 
  log.info banners. The log stream itself is readable enough; adding 
  nested node hierarchy is scope creep for this prompt and couples the 
  report structure to the test's logging style.
- No changes to the test method, page objects, ElementActions, POJOs, 
  or utilities.
- No new Maven dependencies. ExtentReports and Log4j2 already provide 
  everything needed.
- No filtering beyond the logger-name scope in log4j2.xml. Don't add 
  regex filters or marker-based filters. If noise creeps in later, 
  we'll tune then.

## Verification steps before committing

1. `mvn clean compile` — confirm the new appender compiles and 
   Log4j2's plugin cache regenerates (target/classes/META-INF/
   org/apache/logging/log4j/core/config/plugins/Log4j2Plugins.dat 
   should appear).
2. Run the suite once: `mvn clean test`.
3. Open the freshly-generated `reports/extent-report.html` in a 
   browser. Click the test row. Confirm the Details section now shows 
   a multi-line narrative: "Clicking: Log in link", "Typing [...]", 
   "Clicking: search button", etc., down to the final "Test passed" 
   entry. The failure/screenshot path should still work — but don't 
   deliberately break the test to test that; trust the symmetry.
4. Confirm the report file size is under ~500KB. If it's larger, 
   something is over-forwarding (likely DEBUG leaking through) — stop 
   and report.
5. Commit the regenerated `reports/extent-report.html` along with the 
   code changes in the same commit. This replaces the Prompt 06 
   committed report with the richer version.
